# Research: plugins

**Date:** 2026-06-05T13:16:00 | **Status:** research-complete

## Goal
Add the Plugins extensibility layer to the existing Commons RN app: an in-app Apps
directory (browse + mock install), installed-plugin **slots** that render inside Today/You,
and a role-gated Developer console. Mock-data phase — "install" = a store toggle; plugins
are compile-time modules. Distribution/OTA is NOT in scope (DECISIONS.md Phase 2 partial).

## Requirements

### Technical
- [ ] TR1: Extend ADR-0001 registry pattern toward a **slot system** — named insertion points (`'today'`, `'you'`) that plugins declare a `slot` for. This is the DECISIONS.md roadmap step.
- [ ] TR2: New isolated `features/plugins/` module owning AppsScreen, PluginSheet, DeveloperScreen, PluginWidget, plus a `manifest.ts` if it needs registry presence (it does NOT add a tab — entry points are More rows + slots).
- [ ] TR3: **PluginSlot must live in shared infra (`components/` or `lib/`), NOT in `features/plugins/`** — Today and You can't cross-import a feature module (no-cross-feature-imports rule, ADR-0001). Put the `<PluginSlot slot="today" />` component in `components/PluginSlot.tsx`; it reads the plugins store directly (Zustand), and Today/You just drop the element in. This keeps features isolated.
- [ ] TR4: New `lib/stores/plugins.ts` Zustand store: `{ plugins, installed[], developer, showWidgets, toggleInstall(id), setDeveloper, ...selectors }`. This is the single source of truth replacing App.jsx local state. Matches existing store conventions (events/kudos/onboarding/ui).
- [ ] TR5: Overlays — AppsScreen + DeveloperScreen are full-screen pushes. Follow the existing stack-route pattern: thin route files `app/apps.tsx` and `app/developer.tsx` rendering the feature screens, registered in `app/_layout.tsx` Stack (alongside stipend/person/onboarding). PluginSheet follows the existing `Sheet` component pattern (RN Modal, `visible`/`onClose`).
- [ ] TR6: Data types added to `lib/data/types.ts`; data module `lib/data/plugins.ts`. SI/display conventions N/A (no units here).
- [ ] TR7: Tests — store logic (toggleInstall add/remove, slot filtering, role gate), PluginWidget render per kind, AppsScreen/DeveloperScreen smoke, MoreScreen dev-row gating. Follow RNTL act/waitFor pattern (SUMMARY.md retro).

### Constraints
- Expo Go SDK 54, no native modules; demo-on-phone matters today.
- Mock-data only — no persistence (no AsyncStorage), no OTA, no real downloads.
- Surgical changes to 3 demo-critical screens (Today/You/More). Don't restructure them.
- ADR-0001 frozen: don't add a 6th tab; don't edit the registry's tab list.

## Patterns to Follow
- **Stores as source of truth** — `lib/stores/ui.ts` (chrome-level flag store) is the model for the plugins store, esp. `developer`/`showWidgets` (app-shell state, not domain).
- **Full-screen overlays as Stack pushes** — `app/stipend/[id].tsx` → thin route → `features/you/StipendDetailScreen`. Mirror for apps/developer.
- **Cross-feature nav by route path only** — `router.push('/apps')`, never import a feature screen into another feature (TodayScreen.tsx:57-60).
- **Shared cross-boundary UI goes in `components/`** — precedent: `EventCard`, `NotificationsSheet` were promoted to components/ because used across features (SUMMARY.md). PluginSlot is the same case.
- **Sheet = `components/Sheet.tsx`** (RN Modal, `visible`/`onClose`) — PluginSheet wraps it; no external bottom-sheet lib (Expo Go-safe).
- **Per-stream commits + TDD on stores** — retro's strongest wins; write failing store tests first.
- **Reuse primitives** — Button (variant/size/icon), Pill (tone/dot), IconTile, SectionHeader, Icon, Stars-equivalent all exist.

## Patterns to Avoid
- **Don't put PluginSlot in `features/plugins/`** — Today/You importing it violates no-cross-feature-imports. (TR3)
- **Don't add a 6th tab** — chat2.md is explicit: 5 is the ceiling; Apps lives under More, not the bottom bar.
- **Don't replicate the prototype Tweaks panel** — it's a browser postMessage host-protocol shell (`tweaks-panel.jsx`), not portable to RN. Just need an in-app dev-mode toggle.
- **Don't mirror App.jsx's local-state wiring** — the prototype centralizes install/overlay state in one root component; RN should use the Zustand store + per-screen local overlay state (existing convention), not a god component.
- **Conductor/multi-stream-in-one-agent** — retro: failed 2/2. Plan should be stream-by-stream.

## Risks
| Risk | Severity | Mitigation |
|------|----------|------------|
| Touching 3 demo-critical screens (Today/You/More) | M | Slot insertion is a single self-contained element; MoreScreen addition is one card under the hero. Keep diffs minimal; smoke-test each on device. |
| Where to flip `developer` for a live demo (no Tweaks host in RN) | M | Recommend a hidden affordance: long-press the More header or a debug row, OR seed `developer:true` and show both states via the store. Decide in Open Questions. |
| PluginSlot in shared layer reading a feature-adjacent store | L | Store lives in `lib/stores/` (already shared); PluginWidget is pure presentational. No feature coupling. |
| Slot placement on You (prototype put it at end; design intent = "a row on You") | L | Confirm exact insertion point in /plan; default to after "My events". |
| 4 widget kinds = layout variety (countdown is static mock, not live) | L | Mock values only; `next.value` is a static string ("12"), no timer needed. |
| Lucide icon names used (bus, utensils, piggy-bank, hand-heart, code-xml, etc.) | L | Verify each resolves in `lucide-react-native`; substitute if missing. |

## Open Questions
| Question | Resolution |
|----------|------------|
| How to flip `developer` mode in-app for the demo? | **Recommend:** add a `setDeveloper` toggle to the plugins store, exposed via a small debug control — e.g. a "Developer mode" switch row in More's bottom "More" card (visible always, flips the gate live). Simplest, on-device, demo-friendly. Confirm with user vs. seeding `developer:true` permanently. |
| Default state of `developer` / `showWidgets`? | **Recommend:** `showWidgets: true` (slots populated for demo), `developer: true` (so the Developer console is reachable in the demo) — matches prototype defaults. |
| Exact You-tab slot placement? | **Recommend:** after "My events" (end of scroll), matching prototype's trailing slot. Defer fine placement to /plan. |
| Does `features/plugins/` need a registry manifest? | **No** — it adds no tab. Entry points are More rows + slots + stack routes. Registry stays frozen (ADR-0001 honored). |

## Recommended Approach
Add a `lib/stores/plugins.ts` Zustand store (install list + `developer`/`showWidgets` flags)
as the single source of truth, plus `lib/data/plugins.ts`. Build PluginWidget + PluginSlot in
the **shared `components/` layer** so Today/You can render slots without cross-feature imports,
and build AppsScreen/PluginSheet/DeveloperScreen inside an isolated `features/plugins/` module
reached via new thin Stack routes (`/apps`, `/developer`) and two new MoreScreen rows (Apps for
all, Developer role-gated). This extends ADR-0001's registry seam into a named slot system per
the DECISIONS.md roadmap, keeps the 3 demo screens nearly untouched, and stays fully mock/compile-time.

## Scope: M
Net-new code is substantial (1 store, 1 data module, ~5 components/screens, 2 routes, tests) but
mechanically straightforward — pure UI + in-memory toggles, no native modules, no backend, no OTA.
Risk concentrated in 3 small surgical edits to existing demo-critical screens. Naturally
stream-able (data+store → shared widgets/slot → directory+sheet → developer console → screen wiring),
which the retro shows is the reliable execution shape.
